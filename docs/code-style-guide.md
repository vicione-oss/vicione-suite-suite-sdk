# Code Style Guide

## C#

### Sorting

Members of a C# `class`, `struct`, `interface` and `record` are sorted by the following groups.
Groups are separated from each other by a line break.

1. Constants
2. Static fields
3. Other fields
4. Properties
5. Events
6. Constructors
   - Grouped by keyword in order of `static`, `public`, `internal`, `protected`, `private` followed by constructors without keyword
   - Groups are sorted by number of parameters in ascending order
7. Methods

### Test methods

- Test method names should use [snake case](https://en.wikipedia.org/wiki/Snake_case) pattern.

  > The Test Explorer replaces underlines with spaces because of [`our configuration`](/vicione-oss/vicione/vo-suite/-/blob/6fc3db74e4f7627ead5d562436e588ef44089165/xunit.runner.json#L4) of [`methodDisplayOptions`](https://xunit.net/docs/runsettings#MethodDisplayOptions). As a result, test names like `Should_return_access_level_requirement` are displayed as formulated sentences like `Should return access level requirement`.

## Code comments

Comments are read far more often than they are written, and a redundant or stale comment costs more than no
comment at all. These rules apply to every hand-written `*.cs` and `*.razor` file in the solution.

**This repository is the public surface of the suite.** Its XML documentation is what module authors see in
IntelliSense and in the generated API docs, so a doc comment here is a product, not a note to ourselves.

**Out of scope:** generated code is never edited by hand — designer files (`*.Designer.cs`), anything under
`obj/` or `bin/`, any file carrying an `<auto-generated>` header, and the emitted-source string literals in
`Sdk.Backend.SourceGenerators`.

### The two principles

**1. Write down only what the code cannot say.** The code already records *what* happens. A comment earns its
place by adding something the reader cannot get from the code: a reason, a constraint, a trade-off, a
non-local consequence, or a pointer to a decision made elsewhere.

**2. A good name is the better comment.** Before writing a comment, check whether renaming removes the need
for it. A rename helps every caller; a comment helps only the reader standing in front of it.

### Keep these comments

Tighten the wording, but never delete the substance:

- **Why a decision was made**, especially when the obvious alternative was rejected — including references to
  an ADR, an issue, a spec section or a vendor bug.
- **Ordering and placement constraints** that the code cannot express.
- **Platform and third-party quirks**, e.g. behaviour of MassTransit, EF Core or the Edge-S target that
  surprises the reader.
- **Deliberate no-ops**, e.g. why a caught exception is swallowed.
- **Warnings to the next maintainer**, e.g. "add new fields here too" on a mapper.

### Delete these comments

- Anything that narrates the next line: `// open combobox` above `combobox.Open()`.
- Filler XML tags that restate the signature: `/// <param name="cancellationToken">A token to monitor for
  cancellation requests.</param>`.
- Empty XML tags: `<returns></returns>`, `<param name="x"></param>`. If the tag's `cref` carries information,
  fill it in rather than dropping it.
- Commented-out code. Git remembers it. If something is parked for a feature that is not implemented yet,
  leave **one** comment saying so.
- Separator banners (`// -----`), file headers, `#region` labels, and change logs inside files.
- Questions to yourself: `// Extra State needed?`. Answer it, or open an issue.

A `<summary>` on a public member is the exception: it is **rewritten**, never deleted — see below.

### How to write one

| Rule | |
|---|---|
| Form (`///` vs `//`) | A comment describing a declaration is an XML doc comment. Plain `//` is for statements inside a body. |
| Language | en-US only. |
| Voice | Impersonal and present tense. Not "we clear the cache" but "clearing the cache releases the file lock". |
| Tone | Neutral and factual. No exclamation marks, no emoticons, no humour at the code's expense. |
| Length | One comment line stays under 140 characters; one comment block stays under 6 lines. |
| Overflow | Longer rationale belongs in `docs/` or an ADR, with a one-line pointer from the code. |
| Whitespace | No trailing whitespace on a comment line. |

Where a comment is a legend, a group listing or a small table, keep the one-item-per-line layout — the
alignment is what makes it readable, and the line budget does not apply to it.

### XML documentation

**Public members must carry an XML doc comment, and the build enforces it.**
`GenerateDocumentationFile=true` is set for every project in `Directory.Build.props`, nothing suppresses
`CS1591`, and CI treats warnings as errors. A public member without a doc comment fails the build. That is
deliberate: this is the SDK.

Required does not mean ceremonial. A doc comment that only restates the member name has satisfied the
compiler and wasted the reader's time. Lead with the information the signature is missing: the meaning, the
unit, the default, the constraint, what `null` means, what happens on failure, whether it is safe to call
concurrently.

- **`<summary>` is one sentence**, two at most. Do not restate the member name in prose.
- **Keep the `Gets …` / `Gets or sets …` opener** on properties. It tells a module author whether the property
  can be set, so it must match the public accessors; an `init` property reads `Gets or initializes …`. The words
  after the opener still have to say something the name does not.
- **`<param>` is all-or-nothing per member.** `CS1573` fires when *some* parameters are documented and others
  are not, so either document every parameter or none. Prefer none, and reach for the full set only when at
  least one parameter needs a unit, a range, a null-meaning or an ownership rule.
- **`<returns>`** only when the return value is not implied by the method name and return type.
- **`<exception>`** for exceptions the caller is expected to handle. This matters more here than in an
  application repository: an SDK consumer cannot read the implementation to find out what throws.
- **`<inheritdoc />`** on implementations and overrides. Never copy an interface's documentation into its
  implementation — the copy goes stale on the first change to the interface.
- Reference types with `<see cref="..."/>` rather than a bare name, so the reference survives a rename.

```csharp
// Bad - three tags, zero information beyond the signature
/// <summary>
/// Gets or sets the list of repository sources where artifacts are retrieved from.
/// </summary>
public List<ArtifactRepositorySourceOption> Sources { get; set; } = [];

// Good - says the thing the name cannot
/// <summary>
/// Gets or sets the artifact repository sources, queried in declaration order; the first match wins.
/// </summary>
public List<ArtifactRepositorySourceOption> Sources { get; set; } = [];
```

### Markers

Use `// TODO:` and `// HACK:` only, each followed by an issue reference. `XXX`, `FIXME` and a bare `TODO`
without a reference are not accepted — an untracked marker is a comment nobody will ever act on.

```csharp
// TODO(#1423): replace with the ordered outbox once the master-slave sequence lands.
```

### Razor

- `@* *@` only for a structural section label that the markup cannot express. Prefer extracting a named
  component.
- Never use `<!-- -->` for a developer note: an HTML comment is sent to the browser, `@* *@` is stripped at
  compile time.
- Put rationale in the `@code` block or the code-behind, not in the markup.

### Tests

The `// Arrange`, `// Act`, `// Assert` markers are mandatory and stay exactly as they are — they are
structure, not commentary. Beyond those three, a test needs a comment only when the *setup* is
counter-intuitive; the test name carries the intent.

### Samples

Everything under `samples/` is teaching code, so comment it **more** than the rest. Explain the mechanics a
newcomer needs: how a message flows, why a call goes to one endpoint rather than another, what a framework
hook is for. "No need to explain the obvious" does not apply here — what is obvious to us is exactly what
the sample exists to teach. The form rules still hold, and a deliberately missing piece is described in
prose rather than left behind as commented-out code.
